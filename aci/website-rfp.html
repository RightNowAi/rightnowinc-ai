1. Background

Austin Career Institute (ACI) is a vocational trade school operating two campuses in Austin, Texas, offering accredited programs in HVAC-R, Electrical/Renewable Energy, Welding, and Medical Assistant training.

ACI's marketing program has scaled from roughly 50 leads/month to approximately 1,500 leads/month over the past growth period, prompting a second campus and a full rebuild of the underlying marketing and operational infrastructure — including a new CRM (Portico Recruit / Portico EDU, replacing the outgoing CampusLogin system) and this website rebuild.

This RFP is for the design, development, and launch of a new website to replace the current site at austincareerinstitute.edu. The CMS platform is open — vendors should propose the platform they recommend and justify the choice (see Section 3.1). The new site must integrate directly with the Portico EDU CRM via API and function as a conversion-focused lead generation platform — not a static brochure site.

2. Project Objectives

  • Primary: Generate qualified inbound leads (form submissions, calls) from prospective students across four program areas.
  • Secondary: Preserve and grow organic search visibility during and after migration.
  • Tertiary: Provide a cloneable landing page template the marketing team can use to self-serve new paid-media campaign variants without developer involvement.
  • Support a clean handoff from the outgoing CampusLogin CRM to Portico EDU with zero PII stored in the site's CMS.

3. Scope of Work

3.1 Platform & Infrastructure

  • CMS: Open — vendor proposes the platform (e.g., WordPress, a headless CMS, or other open/self-hostable option) best suited to the requirements in this RFP, with a brief rationale. Proposal must state the recommended platform explicitly.
  • Ownership requirement: ACI must own the codebase, hosting account, domain, and all site assets outright — see Section 4. Closed, vendor-hosted SaaS site builders (e.g., Webflow, Squarespace, or similar platforms where the site cannot be exported and self-hosted) do not meet this requirement and should not be proposed.
  • Whatever platform is proposed, it must support: per-page SEO metadata, easy non-technical content editing by ACI staff, a cloneable landing page template, and clean API-based (not embed/iframe) form submission to Portico — see 3.4.
  • CRM: Portico EDU — API integration only. Portico does not host or build the site.
  • DNS/CDN: Cloudflare — full setup including SSL, caching rules, cache-bypass rules on form and thank-you pages, and canonical domain redirect.
  • Coordinate nameserver transfer and cutover timing from the current host; current host is decommissioned post-launch.
  • Portico API documentation will be provided by ACI/RightNow prior to form-build kickoff — vendor should flag this as a scheduling dependency in their proposal.

3.3 Landing Page Templates

  • One master, cloneable landing page template for paid media traffic (Google, Meta, TikTok), applied across four program variants.
  • No main navigation or footer navigation — header logo and phone number only.
  • Form above the fold on both desktop and mobile.
  • Same Portico API POST and hidden-field spec as site forms (see 3.4).
  • Noindex; one corresponding thank-you template.
  • Template must be usable by the marketing team to create new campaign variants without developer involvement.

3.4 Forms, Tracking & CRM Integration

  • Custom form build — no CampusLogin embeds, no iframe dependency.
  • Every form POSTs directly to the Portico API; the CMS is UI layer only — no PII stored in the CMS/site database under any circumstances (non-negotiable, see Section 4).
  • Hidden fields auto-populated from URL parameters on every form: gclid, utm_source, utm_medium, utm_campaign, utm_content, utm_term, landing_page_url.
  • Parameters persist through the full traffic chain: ad click → landing page → form → thank-you page.
  • Full GTM migration with Consent Mode v2; conversion trigger fires client-side on submission, before or simultaneous with the API POST.
  • Form success/error states handled in-UI — no page reload.

3.5 SEO & Metadata Migration

  • Maintain existing URL structure wherever possible; full 301 redirect map where URLs must change (RightNow provides the map, vendor implements).
  • Zero broken links or 404s at launch.
  • Migrate all existing metadata: title tags, meta descriptions, Open Graph, Twitter Card, canonical tags, robots directives, and existing schema markup.
  • SEO tooling appropriate to the proposed CMS (e.g., RankMath/Yoast if WordPress, or equivalent) must support per-page metadata on all post types and templates.

3.6 Accessibility & Compliance

  • WCAG 2.1 AA compliance built into the design and templates — no overlay/widget plugins as a substitute for compliant markup.
  • Content and claims are subject to Texas Workforce Commission (TWC) and U.S. Department of Education regulations governing vocational schools — vendor is not responsible for content compliance, but the CMS must support easy content edits by ACI's compliance-reviewing staff.

4. Hard Requirements (Non-Negotiable)

  • Full ownership: ACI owns the website outright — codebase, hosting account, domain, CMS installation/license, and all site assets (images, content, design files). Nothing developed under this contract may be vendor-owned, vendor-hosted-only, or reliant on a proprietary platform ACI cannot independently access, export, or migrate away from at any time.
  • Hosting is set up under an ACI/RightNow-controlled account from day one (or transferred to one at launch) — not a vendor's agency-level or reseller account. Vendor may recommend a host but does not retain administrative control post-launch.
  • All credentials (hosting, domain registrar, CMS admin, Cloudflare, repository) are handed over to ACI/RightNow at launch as a deliverable — see Section 5.
  • Full source code, including any custom theme/template or plugin development, is delivered to ACI/RightNow in a version-controlled repository (e.g., Git) that ACI owns.
  • No PII stored in the CMS/site database under any circumstances — no form entry logging, no admin inbox entries, no CMS-side email notifications. All lead data and notifications are handled by Portico.
  • Extension/plugin audit required before launch — vendor documents any plugin, app, or integration that collects, stores, or transmits user data, and confirms none violate the no-PII rule.
  • Mobile-first build.
  • No page reload on form submission.
  • All landing pages and thank-you pages set to noindex.

5. Deliverables

  • Fully built, tested, and launched site meeting the scope above, on the vendor's proposed CMS.
  • Full ownership transfer: all hosting, domain registrar, CMS admin, Cloudflare, and repository credentials handed over to ACI/RightNow, with ACI/RightNow as the account owner of record — not the vendor.
  • Complete source code delivered in a Git repository owned by ACI/RightNow.
  • Cloneable landing page + thank-you page template set, with documentation for marketing-team self-service.
  • Completed 301 redirect implementation.
  • Plugin audit report (data collection/storage/transmission per plugin).
  • Documentation: CMS editing guide, form/CRM integration overview, Cloudflare configuration summary, and a punch list of any post-launch items.
  • 30-day post-launch support window for bug fixes (vendor to confirm terms in proposal).
